Semantic Software Design

Design starts with meaning: name the concepts of the business before choosing any technology.

Eben Hewitt · 2019

What the book is about

Eben Hewitt argues that software is a language artifact before it is a technical one. Systems fail on vague concepts and names more often than on code, so the first job is to design the concepts.

Ideas I took from it

  • A shared vocabulary does more than a framework choice.
  • Ambiguity is the most expensive defect. A vague term spreads silently into data, screens and decisions.
  • Technology decays; clear concepts compound.

On a Build Day

We start by naming the few things your tool is about (a customer, an invoice, a visit) and what each one means, before the AI writes anything.

Concepts behind it

  • Meaning Before Mechanism — A semantic model is not a technology. The same meaning can ship as a graph, an API, a data product or a contract — decide what it means before deciding what to buy.
  • Model the Meaning You Need — The enterprise ontology that models everything ships nothing. Grow shared meaning one high-value use case at a time — and leave batch_id alone.
  • Metadata First — Metadata is the material Breakthrough Modeling is built from — structure, logic and meaning captured as data, so the platform and the AI can both read and run it.
