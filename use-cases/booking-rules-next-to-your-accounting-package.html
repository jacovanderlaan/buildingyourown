Accounting and bank transactions

Keep the accounting package, own the booking rules

The official books stay in the accounting package. The knowledge of how things are booked moves out of people's heads into a readable rule file, and a mirror of the books makes them queryable.

Replaces
nothing — works next to the accounting package (Snelstart)
Built with
YAML rules, Python, DuckDB, an MCP server for questions in plain language
In numbers
11,587 bookings · 155 ledger accounts · about 41 booking rules

The situation

A small company's books live in an accounting package, and the rules for booking them live in the head of one person — the owner or the bookkeeper. Which bank line goes to which ledger account, with which VAT? When that person is away, nobody knows.

What I built

  • A rule file: match pattern → ledger account → VAT code. Around forty rules cover almost every recurring line.
  • A mirror of the bookkeeping export in a local database, so I can ask questions the package makes hard: profit and loss per quarter, open invoices, revenue per customer.
  • A small assistant connection (MCP) so I can ask those questions in plain language.

The package stays the official record. Nothing is booked twice.

The structure underneath

Booking knowledge is data, not habit. A rule can be read, discussed with the accountant, versioned, and applied by a script or by an AI — the same rule every time.

What it taught me

Agree with your accountant which year is closed. A frozen year is never corrected by hand; corrections go through the next period. The rule file makes that discipline easy to keep.

Start on a Build Day

Bring an export of one quarter of bank lines and your chart of accounts. Write the first ten rules together, then let the AI suggest the next ones — and check every suggestion against the rule format.

Concepts behind it

  • Rules as Data — Constraints and logic expressed as data, not buried in code — rules say what must hold, versioned and enforceable, so quality and governance travel with the model.
  • Rules You Can Verify — '2-space indent' is a rule; 'format code properly' is a wish. A rule the system can't check is decoration.
  • Own the Layer or Rent the Feature — Every knowledge product answers two questions: who maintains it, and is it a layer of its own or a feature of something else. The answers decide what you can build on.
