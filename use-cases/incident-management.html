The rest of the business OS

Incident management that turns every failure into a rule

Every disruption — a failed import, a broken page, a dispute with a supplier — becomes a small file with an owner, a status and a lesson. The lesson becomes a rule, so the same failure does not come back.

Replaces
tickets in someone's mailbox, or nothing at all
Built with
one markdown file per incident with fixed fields, a control table, a dashboard and cockpit screen
In numbers
51 incidents tracked · 36 open, 15 closed

The situation

In a small company, things go wrong quietly. An export fails, a page breaks, a supplier delivers late. Someone fixes it, nobody writes it down, and three months later it happens again.

What I built

  • One file per incident, with fixed fields: kind (defect, service, dispute), status, severity, owner, dates, and the parties involved. The body has the situation, a timeline, the fix and the lesson.
  • A control table that collects incidents together with actions and ideas, so open incidents show up on the same dashboard and in the same cockpit as everything else.
  • Bugs found by automated checks are turned into incidents automatically.

Three real ones

  • A generator that erased work. A script rewrote 1,399 weekly notes and wiped 24 sections written by hand. It had a protection — which judged a section before removing a placeholder comment. Lesson: base safety on a measurement, not on a report; a half-working protection is worse than none.
  • A backup that read everything again. A cold backup re-read 833 GiB and a million files in four hours instead of minutes, because two snapshots spelled the machine name differently. No data lost — but measure which convention is the norm before you fix the outlier.
  • A blank app. One line used a value before it was defined, and the whole single-page app went white — three times. A syntax check does not catch it; a small runtime test does.

What the data says

The status field itself turned out to be the weak spot: fixed, resolved, closed and a few free-text variants all mean roughly the same. An incident system needs its own rules too.

The structure underneath

An incident is data, not a story. Once it has fields, you can count, sort and see patterns — and every fix can become a rule or a check.

Start on a Build Day

Bring the last five things that went wrong. Give them the same five fields, and write one rule per incident that would have caught it.

Concepts behind it

  • Incident Modeling — Model delivery incidents as data, not loose tickets — a late feed, a failed quality check, a broken schema becomes a tracked, owned, queryable object in the model itself.
  • The Mistakes File — Same mistake twice = a new rule. Corrections you'd otherwise repeat forever get written into a file the AI reads every run.
  • Escalate by Exception — Route the easy work to the cheap path and reserve the expensive one for what actually needs it. Power by exception, not by default.
