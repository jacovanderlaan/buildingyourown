Build Your Own Apps

Small working tools on your own files: a lookup page, a checklist, a form that writes to the right place.

Duration: half a day · Builds on: Memory · Models · Pipelines

A dashboard shows you something. An app lets you do something with it. With AI typing the code, the hard part is deciding what the app should do, and that part is yours.

You leave with

  • One small app that runs on your laptop and reads your own files or database, for example a customer lookup or a daily checklist.
  • A one-page spec for it: who uses it, what goes in, what comes out, what it must never change.
  • A second screen added as configuration only, without new code, so you see how the next app gets quick.
  • A short test you can run again after every change.

Ideas to try

  • A bike shop types a frame number and sees the owner, the last service and what was replaced.
  • A plumber opens a checklist per job type on the phone, and the finished list is saved in the job's note.
  • A physiotherapy practice has an intake form that writes a new client note with the right header fields.
  • A bed and breakfast gets a page that shows today's arrivals, their room and any diet wishes, from the booking export.
  • A freelance translator keeps a rate calculator that uses last year's real hours per client.

Your turn

Which small task do you do by hand every day because no tool fits it exactly? Bring the files that task uses.

What we do in the session

  1. 20 min — Pick one job for the app and write the one-page spec together. One user, one task.
  2. 30 min — Shape the data the app reads into one table or one folder of notes with the same fields.
  3. 70 min — Build the first screen with Claude Code. You describe, the AI types, you check every result against your own data.
  4. 30 min — Test with real input, including the odd cases: an empty field, a duplicate, a name with an accent.
  5. 30 min — Add a second list as a configuration row, and write down the rule that made it easy.

What you bring

  • A laptop and the files or export the app will read (a client list, a product list, a booking export).
  • One task you would like the app to do, described in two sentences.

Tools

Claude Code for the building; a browser to run the app; your Memory and, if you have one, a DuckDB file from the Pipelines level. Optional: a phone to try the screen on.

Example from my own system

My own system runs on a small set of building blocks: list, table, cards, timeline, board, a document viewer, filters and a search. Thirteen small apps share one shell, and 156 screen areas are rows in a configuration file instead of code. Adding a screen means adding a row: label, entity, view, filter. See Building blocks that make the next app quick.

Pitfalls

  • Building every app from scratch. I had three copies of the same path logic, and they gave three different bugs. Build the list view once and reuse it.
  • Letting the app write without a dry run. An app that changes your source files should first show what it would change. Make that the default.
  • Sharing it too early. My apps are built for one person on a private network, without a login. Before a colleague uses one, it needs access control. That is the Safeguards level.

Works best after

Memory, Models and Pipelines. An app is only as good as the data it reads: with folders, a model and one clean import in place, the app itself is the quick part.

Concepts behind it

  • Vibe Coding — Use AI to quickly build real things — especially nice interfaces on top of the metadata — to explore, prototype and give people a way in. Great for experimenting; just don't ship the unspecified, ungated style to production.
  • Decompose and Compose — Break the complex whole into small, self-contained parts you can name, model and check one at a time — the core move of thinking in structures.
  • Play with the Blocks — Like Lego — snap, try, rebuild. Tinker in your own life to learn what's possible.
  • Fail Fast — Set experiments up to fail quickly and cheaply, read the signal honestly, and move on — don't linger in something that, in the end, may not work.

Resources

  • Claude Code — The AI coding tool most of the use cases on this site were built with. Strong when it gets a spec, rules and a way to check its own work.
  • The Pragmatic Programmer (20th anniversary edition) — Tracer bullets, small steps, don't repeat yourself. Written for programmers, and more relevant now that the AI is the one typing.
  • Tiny Experiments — Treat a change as an experiment with a fixed duration instead of a goal. The same move is what makes a Build Day work: one small build, then decide.
