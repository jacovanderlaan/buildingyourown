Vibe Coding Without the Hangover

Eight practices that keep the speed of AI-written code and drop the surprises

By Jaco van der Laan

Vibe coding — describing what you want and letting the AI write the code — is how most of my own tools were built this year. It is fast enough to change what is worth building. It also produces a particular kind of hangover: code that works on the first try, looks finished, and is wrong in a way nobody notices for weeks.

These are the practices I use to keep the speed and lose the hangover. None of them needs programming skill. All of them need discipline.

1. Write the spec, not the prompt

A prompt asks for code. A spec says what must be true when the code is done: which input, which output, which cases must be refused. Write the spec in a file, not in the chat. The next session, the next tool, and the next person can read it.

2. Give the AI a standing instruction file

Every project gets one file the AI reads first: what this project is, where the data lives, what must never be touched, which mistakes were made before. Mine grew from a few lines to a page per project, and every line in it is a correction I did not want to make twice.

3. Keep a mistakes file

When something goes wrong, write the lesson down in one line, in the place the AI will see next time. A rule like Chrome sync wins from the local bookmarks file came from 783 old bookmarks reappearing on top of 11 new ones. Written down once, it never happened again.

4. Rules as data, not buried in code

If the tool applies business rules — categories, booking accounts, visibility, naming — keep them in a readable file, one rule per line. The AI can write the code that applies them; you keep control of the rules themselves. Changing a rule should not need a new conversation with the AI.

5. Dry run by default

Anything that writes, moves, deletes or sends must first show what it would do. My photo pipeline handles more than 200,000 files; every step runs dry unless told otherwise, and 35 tests guard the rules. A dry run costs seconds. A wrong move on 200,000 files costs a weekend.

6. The AI does not mark its own homework

The AI will tell you it succeeded. Believe the count, not the message. After every run, check against reality: how many files arrived, how many rows are in the table, does the page actually show the image? A confident error looks exactly like a correct answer. One of my site builds reported success while 37 pages had broken images. Now the build checks its own output and fails when a link does not resolve.

7. Small steps, each one saved

Let the AI change one thing at a time, and save a version after each step that works. When step seven breaks something, you go back to step six, not to the beginning. This is old advice for programmers. It matters more now, because the AI changes more per step than a person would.

8. Look at what it made

Read the output yourself, at least the first time. Open the page, look at the image, scan the table. Several generated images on my own sites had garbled text or the wrong colours; they were only caught because looking at each one before use is a fixed step.

The pattern behind all eight

Each practice moves something out of the conversation and into a file or a check: the spec, the instructions, the mistakes, the rules, the counts. The conversation with the AI is where the speed comes from. The files and the checks are where the reliability comes from. You need both, and only the second one is yours to keep.

Use cases in this article

  • Document intake that keeps its own receipts
  • A photo pipeline that knows what is private
  • From phone scan to the right folder, named and indexed

Concepts behind it

  • Vibe Coding — Use AI to quickly build real things — especially nice interfaces on top of the metadata — to explore, prototype and give people a way in. Great for experimenting; just don't ship the unspecified, ungated style to production.
  • Write the Spec, Not the Prompt — A prompt is a request you repeat. A spec is a contract the work is checked against — and it is the artefact that survives the session.
  • CLAUDE.md as Operating System — Standing rules the AI reads before it acts — a layered OS for how the assistant behaves in your world.
  • Never Marks Its Own Homework — The judge must be separate from the builder, and the score is the off-switch: a loop only stops when an independent evaluator says the rubric is met.
  • The Mistakes File — Same mistake twice = a new rule. Corrections you'd otherwise repeat forever get written into a file the AI reads every run.
  • A Confident Error Has No Tell — A hallucination arrives in exactly the same shape as a correct answer. That is the whole problem — and why fluency is not evidence.
  • Hooks Over Hopes — Every instruction to a model is a probability, not a promise. Rules that must always run belong in deterministic automation the model can't skip.
  • Rules as Data — Constraints and logic expressed as data, not buried in code — rules say what must hold, versioned and enforceable, so quality and governance travel with the model.
